# SerpBear MCP OAuth Implementation Plan

> **For agentic workers:** Implement task-by-task in this session; preserve the current `oauth` branch and its clean-base history.

**Goal:** Add standard OAuth connection support to SerpBear's single-account read-only MCP server while keeping direct `MCP_API_KEY` access.

**Architecture:** Add OAuth protocol routes beneath `/api/oauth`, well-known discovery routes for MCP, a themed approval page, and JSON-backed client/code/token records in `data/mcp_oauth.json`. The approval page uses the normal SerpBear login session. `/api/mcp` validates either `MCP_API_KEY` or an OAuth access token; existing internal API calls continue to use `APIKEY`.

**Tech Stack:** Next.js App Router, TypeScript, MCP SDK, Web Crypto/Node crypto, existing shadcn components, atomic JSON file storage.

**Spec:** `docs/superpowers/specs/2026-11-10-mcp-oauth-design.md`

## Global Constraints

- OAuth API paths are under `/api/oauth`.
- `MCP_API_KEY` is optional and only used for direct MCP bearer access; OAuth approval uses the normal SerpBear login.
- Keep MCP tools single-account and read-only.
- Store OAuth credentials as hashes in `data/mcp_oauth.json`, and never log raw secrets.
- Approval page uses SerpBear theme and login-page simplicity.
- Update `CHANGELOG.md`, `.env.example`, `docker-compose.yml`, and `docs/API-and-MCP.md`.

## Review Focus

- Unregistered or non-HTTPS redirect URIs must not receive codes.
- Missing, invalid, expired, or replayed codes/tokens must not authorize MCP requests.
- PKCE must reject missing challenge data, non-S256 methods, and incorrect verifiers.
- Reuse of a rotated refresh token must not authorize the MCP request.
- Missing `MCP_API_KEY` must not disable OAuth authentication or fall back to `APIKEY`.
